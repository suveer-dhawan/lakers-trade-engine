# CLAUDE.md — Project Context for AI Assistants

## What This Project Is
A data science research project building an NBA player valuation and trade analysis engine.
The primary lens is the Los Angeles Lakers and roster optimization around Luka Dončić, but the
underlying model is league-wide and team-agnostic by design.

## Repo Structure
- `src/data/` — Ingestion and caching from nba_api, Basketball Reference, Spotrac, EPM sources
- `src/features/` — Feature engineering: player valuation, Luka complement score, roll gravity
- `src/models/` — Age curves, trade evaluation, pick value, clustering
- `src/utils/` — CBA rules, salary matching, constants
- `notebooks/` — Numbered sequentially. These ARE the documentation. Each has markdown cells
  explaining methodology before code cells implementing it.
- `dashboard/` — Streamlit app (Phase 2B scaffold complete)
- `data/cache/` — Parquet files from API calls. Gitignored. Regenerated by running the pipeline.
- `blog/` — Write-up drafts

## Key Design Principles
1. **Generalize first.** Build league-wide valuation before applying team-specific filters.
   The Lakers lens is a query layer, not baked into the model.
2. **Empirically derived archetypes.** Don't pre-select features for clustering based on what
   we think Luka needs. Cluster all players on all features, then observe which clusters
   successful Luka teammates fall into.
3. **Contractual utility matters.** Surplus value alone is insufficient under the new CBA.
   Expiring deals and multi-year deals have different trade utility under second-apron rules.
4. **Acknowledge system effects.** Player efficiency is partly a product of their teammates.
   We measure output, not isolated quality. State this limitation; don't hide it.
5. **Document as you code.** Notebook markdown cells explain the why before the code implements
   the what. The notebooks are the portfolio deliverable, not just scratch work.

## Technical Conventions
- Python 3.10+. Dependencies in pyproject.toml.
- All API calls go through `src/data/cache.py` — never hit an API without caching.
- Rate limits: nba_api = 0.6s delay, Basketball Reference = 3s delay.
- Data joins use PLAYER_ID (nba_api numeric ID) as the primary key. BBRef and salary data
  join on normalized player name with a manual override dict for edge cases.
- Parquet for all cached data. No CSVs in the pipeline (CSVs only for manual data entry).
- Logging via Python stdlib logging, not print statements (except in notebooks).

## What NOT To Do
- Don't touch the dashboard until Phase 3 polish (current state = scaffold, functional but not pretty).
- Don't use deep learning. Dataset is too small; interpretable models only.
- Don't over-engineer name matching. Simple normalization + manual override dict.
- Don't hit APIs without going through the cache layer.
- Don't create Lakers-specific logic in the core valuation model. Team-specific analysis
  happens in notebooks and the dashboard query layer, not in src/.
- Don't update CBA thresholds without a verified source (ESPN Bobby Marks or NBA.com official).
